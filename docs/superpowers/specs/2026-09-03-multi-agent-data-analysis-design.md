# 多 Agent PostgreSQL 数据分析 Web 应用设计

## 1. 文档状态

- 日期：2026-09-03
- 状态：已完成交互确认，待用户复核书面规格
- 项目阶段：单用户本地 MVP

## 2. 项目目标

构建一个在本地运行的 Web 应用。用户连接 PostgreSQL 后，可以用自然语言提出数据问题；系统通过多个职责明确的 Agent 理解问题、检索数据库结构、生成与审查 SQL、执行只读查询、分析结果并生成交互图表。

系统需支持 OpenAI、DeepSeek 和 Qwen API，并允许用户在界面中切换供应商及模型。

## 3. 成功标准

MVP 完成时必须满足以下条件：

1. 用户可以配置并测试一个 PostgreSQL 只读连接。
2. OpenAI、DeepSeek、Qwen 均可独立配置，并能在相同 Agent 工作流中切换使用。
3. 支持筛选、排序、分组、聚合、表连接和时间趋势六类自然语言查询。
4. 每次成功查询均可展示结论、结果表格、生成的 SQL，以及适用时的交互图表。
5. 危险或非只读 SQL 必须在执行前被确定性规则阻止。
6. SQL 校验或执行失败时最多自动修复两次，随后向用户返回清晰错误。
7. 连续追问能够继承必要上下文，例如在上一轮结果上继续按月份或地区拆分。
8. 示例评测集能够自动检查 SQL 执行成功率和答案正确性。
9. 项目可通过清晰的本地命令启动，并提供配置说明与示例数据库。

## 4. 范围

### 4.1 MVP 范围内

- 单用户、本地运行的 Web 聊天界面
- 一个活动的 PostgreSQL 数据源
- 自然语言到 PostgreSQL SQL
- 多 Agent 编排与逐节点进度展示
- 只读 SQL 审查与执行
- 查询结果表格、CSV 导出和 Plotly 图表
- 多轮上下文、重新运行、停止任务和切换模型重新分析
- 本地会话、配置元数据和审计记录

### 4.2 MVP 范围外

- 数据写入、更新、删除或数据库管理
- 多用户登录、权限系统和多租户隔离
- 云部署、计费和配额管理
- 多数据库联合查询
- 定时任务与主动告警
- 可自由拖拽的仪表盘编辑器
- 任意代码执行或由模型生成并运行 Python/JavaScript

## 5. 技术架构

### 5.1 技术栈

- 前端：React、TypeScript、Vite
- 后端：Python、FastAPI
- Agent 编排：LangGraph
- PostgreSQL 访问：SQLAlchemy 2.x、psycopg 3
- SQL 解析与策略检查：SQLGlot
- 图表：Plotly.js
- 应用本地存储：SQLite
- 配置：`.env` 与本地设置文件；密钥不进入前端持久化存储
- 测试：pytest、前端组件测试、Playwright 端到端测试

### 5.2 分层

1. **Web 交互层**：接收问题，展示流式进度、结论、表格、图表、SQL 和错误。
2. **Agent 编排层**：LangGraph 保存结构化任务状态并控制节点、分支、重试和暂停追问。
3. **安全查询层**：读取元数据，执行确定性 SQL 校验，通过只读连接运行查询。
4. **模型适配层**：向三个模型供应商提供统一调用接口，隔离供应商差异。

前端和后端作为两个本地进程运行。Docker Compose 可作为便捷启动方式，但不作为开发时的唯一运行路径。

## 6. 模型适配层

### 6.1 统一接口

定义 `LLMProvider` 抽象接口，最少提供：

- 同步或异步聊天调用
- 流式文本输出
- 结构化 JSON 输出
- 超时、重试和错误归一化
- 请求用量元数据（供应商返回时记录）

每个供应商配置包括：

- `provider`
- `api_key`
- `base_url`
- `model`
- `timeout_seconds`
- 可选的供应商专属参数

### 6.2 供应商实现

OpenAI、DeepSeek 和 Qwen 共享 OpenAI 兼容的基础传输实现。供应商适配器负责默认地址、模型参数差异、错误映射和能力声明。业务 Agent 只依赖统一接口，不直接导入供应商 SDK。

对不完全一致的结构化输出或工具调用能力，适配器必须进行能力检测或降级为“JSON 文本 + Pydantic 校验 + 有限重试”，不得假设所有供应商行为完全一致。

### 6.3 密钥处理

- API Key 仅保存在后端本地环境或用户选择的本地配置文件中。
- API Key 不通过查询接口返回给前端。
- 日志、异常和审计记录必须对密钥及认证头脱敏。
- 设置页只显示密钥是否已配置，不回显完整值。

## 7. Agent 与工具边界

### 7.1 Coordinator Agent

- 判断请求是数据库查询、结果追问、非数据问题还是需要澄清的问题。
- 生成结构化分析计划。
- 控制工作流路由。
- 汇总最终回答。
- 不直接执行 SQL。

### 7.2 Schema Agent

- 从元数据工具获取表、字段、类型、主外键和允许的统计信息。
- 根据问题筛选相关 Schema，避免把完整数据库结构发送给模型。
- 不主动读取无关业务数据。

### 7.3 SQL Agent

- 根据用户问题、分析计划和相关 Schema 生成 PostgreSQL SQL。
- 输出结构化对象：SQL、查询意图、字段解释和预期结果结构。
- 接收审查或数据库错误后生成修复版本。

### 7.4 SQL Reviewer Agent

- 检查 SQL 是否满足用户问题。
- 检查连接关系、过滤条件、时间粒度和聚合逻辑。
- 输出通过、拒绝或修改建议。
- Reviewer 只提供语义审查，不能替代确定性安全校验。

### 7.5 Analysis Agent

- 基于查询结果生成描述性统计、趋势、异常和关键指标。
- 明确区分数据事实与模型推断。
- 数据不足时返回不足原因，不强行生成结论。

### 7.6 Visualization Agent

- 根据分析意图、字段类型和数据规模选择图表。
- 只输出受限的 Plotly 图表规格，不输出任意前端代码。
- 不适合制图时选择表格或指标卡，并提供理由。

### 7.7 确定性工具

以下能力是普通程序工具，不是自主 Agent：

- PostgreSQL 元数据读取器
- SQL 解析与安全策略检查器
- 只读 SQL 执行器
- 结果采样与摘要器
- Plotly 规格校验器
- 审计日志写入器

模型不能绕过这些工具直接连接数据库或执行代码。

## 8. LangGraph 工作流

共享状态使用 TypedDict 或 Pydantic 明确定义，至少包含：

- 会话与请求标识
- 用户原始问题和多轮上下文摘要
- 当前供应商与模型
- 分析计划
- 相关 Schema
- 候选 SQL 与修复次数
- Reviewer 结果和确定性校验结果
- 查询结果元数据与受限数据
- 分析结论
- 图表规格
- 当前节点、进度事件和错误

主流程：

1. Coordinator 判断意图。
2. 如果问题含糊，工作流暂停并要求用户澄清。
3. Schema Agent 获取相关元数据。
4. SQL Agent 生成候选 SQL。
5. SQL Reviewer 做语义审查。
6. 确定性检查器执行安全校验。
7. 只读执行器运行查询。
8. Analysis Agent 与 Visualization Agent 基于同一受限结果进行处理；实现允许并行，但首版可先顺序执行以简化错误呈现。
9. Coordinator 汇总最终回答。

修复循环：

- Reviewer 拒绝、确定性检查失败或 PostgreSQL 返回可修复错误时，回到 SQL Agent。
- 整个请求最多修复两次，而不是每类错误各重试两次。
- 超过上限后停止执行，并返回最近一次脱敏错误和建议。

## 9. PostgreSQL Schema 检索

- 从 `information_schema` 和 PostgreSQL 系统目录读取允许范围内的元数据。
- 用户可以配置允许访问的 Schema、表和字段。
- 使用表名、字段名、注释、外键和问题关键词进行相关性筛选。
- MVP 不引入向量数据库；先采用确定性关键词评分与有限的模型重排。
- 可以读取低敏感度的轻量统计信息，例如行数估计、时间范围和低基数字段的有限枚举；默认不向模型发送原始样本行。
- 若 SQL 生成确实需要样本值，必须经过字段允许列表、脱敏规则和数量限制。

## 10. SQL 安全模型

数据库安全依赖三层控制：

1. PostgreSQL 专用只读账户与最小权限。
2. 程序侧 SQL AST 校验和执行限制。
3. SQL Reviewer 的语义检查。

程序侧必须执行：

- 只允许单条 `SELECT`，或最终为只读 `SELECT` 的 `WITH` 查询。
- 禁止 DDL、DML、事务控制、权限变更、存储过程调用和多语句。
- 拒绝无法可靠分类的语句，而不是尝试执行。
- 对表和字段执行允许列表检查。
- 开启只读事务和 `statement_timeout`。
- 设置最大返回行数；在安全前提下由外层包装查询应用硬限制。
- 设置结果字节数上限，防止单行大对象绕过行数限制。
- 取消请求时向数据库驱动发送取消信号，并释放连接。

即使程序校验存在缺陷，数据库账户也不应拥有写权限。

## 11. 数据处理与隐私

- 大结果集不完整传给模型。
- 模型输入仅包含字段信息、聚合结果、受限样本和程序生成的统计摘要。
- 敏感字段可通过配置完全隐藏、仅允许聚合或进行掩码处理。
- 最终回答应标明结果行数、截断状态和统计口径。
- 不记录完整查询结果；本地会话只保存必要摘要和可选的小型结果缓存。

## 12. Web 交互设计

### 12.1 设置页

- PostgreSQL 主机、端口、数据库名、用户名和密码配置
- 连接测试
- 允许访问的 Schema、表和字段配置
- OpenAI、DeepSeek、Qwen API 配置
- 默认供应商与模型选择
- 查询超时、最大行数和最大结果大小

### 12.2 聊天页

- 自然语言输入框与模型选择器
- 停止任务按钮
- Agent 节点的实时状态与耗时
- 最终结论
- 可交互 Plotly 图表
- 可分页结果表格
- 可折叠 SQL 与复制按钮
- CSV 导出、重新运行、切换模型重新分析
- 可展开的执行轨迹和脱敏错误

### 12.3 传输方式

普通配置与历史接口使用 REST。Agent 执行进度和增量回答使用 Server-Sent Events。SSE 对单向进度流足够简单；任务取消通过独立 REST 请求完成。

## 13. 本地应用数据

SQLite 保存：

- 会话和消息
- 请求状态与 Agent 轨迹
- SQL、耗时、结果行数和执行状态
- 非敏感设置
- 可选的小型结果缓存

数据库密码和模型 API Key 不写入 SQLite。默认通过 `.env` 提供；后续如需界面持久化密钥，应使用操作系统密钥链，属于 MVP 后增强项。

## 14. API 边界

后端至少提供以下逻辑接口：

- 数据库配置验证与连接测试
- 模型供应商配置验证
- 创建查询请求
- 订阅查询进度事件
- 取消查询请求
- 获取会话和历史消息
- 获取结果表格与图表规格
- 导出 CSV

所有返回对象使用稳定的 Pydantic Schema。错误响应包含机器可读错误码、用户可读说明和请求标识，不包含密钥、认证头或未脱敏数据库错误。

## 15. 错误处理

### 15.1 模型错误

- 对超时、限流和临时网络错误进行有限的指数退避重试。
- 对结构化输出解析错误执行一次格式修复请求。
- 供应商不可用时不自动切换到另一供应商，避免未获用户同意的数据外发；由用户选择是否切换。

### 15.2 SQL 错误

- 可修复错误进入统一的最多两次 SQL 修复循环。
- 仅向模型提供脱敏错误、相关 Schema 和候选 SQL。
- 权限拒绝、危险语句和超时默认不自动扩大权限或放宽限制。

### 15.3 业务歧义

- 指标、时间范围或维度存在多种合理解释时暂停执行。
- Coordinator 生成一个简短、具体的澄清问题。

### 15.4 数据不足

- 明确说明缺少哪些字段或记录。
- 不生成带有推测数据的图表。

## 16. 可观测性与审计

每次请求记录：

- 请求标识和时间
- 供应商与模型
- Agent 节点开始、结束、耗时和状态
- 最终执行 SQL
- 修复次数
- 返回行数、截断状态和总耗时
- 脱敏错误码

禁止记录：

- API Key、数据库密码和认证头
- 未配置允许记录的完整查询结果
- 模型隐藏推理内容

## 17. 测试策略

### 17.1 单元测试

- 三个供应商适配器的请求映射与错误归一化
- SQL AST 分类、允许列表、行数与大小限制
- Schema 相关性筛选
- Plotly 规格白名单校验
- 脱敏与日志过滤

### 17.2 Agent 节点测试

使用固定模型响应测试每个节点的：

- 输入输出 Schema
- 无效结构化结果
- 数据不足和歧义
- SQL 修改建议
- 供应商能力差异

### 17.3 工作流测试

- 正常查询
- Reviewer 拒绝后修复
- SQL 解析拒绝
- PostgreSQL 错误后修复
- 达到修复上限
- 用户澄清后恢复
- 模型超时、限流和任务取消
- 多轮追问

### 17.4 集成与端到端测试

- 使用容器化 PostgreSQL 示例销售数据库。
- 验证只读权限、超时、取消和返回限制。
- 从 Web 提问到图表展示执行完整流程。
- 对固定问题集校验结果值，而不仅校验 SQL 是否成功运行。

## 18. 示例评测集

示例数据库包含客户、订单、订单明细、产品和区域等表。评测集至少覆盖：

- 简单筛选与排序
- 单表聚合
- 多表连接
- 按日、月或季度的趋势
- Top N 与占比
- 同比或环比
- 空值和重复记录处理
- 含糊指标的澄清流程
- 被安全策略拒绝的恶意请求

评测输出记录执行成功、结果正确、是否发生修复、模型调用次数和总耗时。成本仅在供应商返回用量时估算，不作为首版硬性验收门槛。

## 19. 实施边界与顺序

实施计划应遵循以下依赖顺序：

1. 项目骨架、共享 Schema 和配置系统
2. PostgreSQL 元数据与只读执行安全层
3. 统一模型适配层
4. 各 Agent 节点与 LangGraph 工作流
5. REST/SSE 后端接口
6. Web 设置页与聊天结果界面
7. 示例数据库、自动评测和端到端验证
8. Docker Compose 与使用文档

各阶段必须先完成对应测试，再进入依赖其行为的下一层。

## 20. 已确认决策

- PostgreSQL 是 MVP 唯一目标数据库。
- 产品为单用户本地 Web 应用。
- 支持 OpenAI、DeepSeek 和 Qwen API。
- 模型接入采用轻量统一适配层，而非独立原生 SDK 或外部模型网关。
- 多 Agent 编排采用 LangGraph 状态图。
- Agent 通过结构化共享状态协作，不使用无限制自由群聊。
- 数据库只能只读访问，模型不能直接执行 SQL 或任意代码。
